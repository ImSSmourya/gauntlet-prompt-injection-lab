# Gauntlet

## Project overview

Gauntlet is a local prompt-injection security demonstration and hackathon prototype. It compares an unguarded simulated agent with a least-privilege agent and provides three selectable permission profiles for exploring how tool access changes an agent's capabilities.

The localhost dashboard presents simulated scenarios, attempted tool calls, permission outcomes, execution status, and event traces.

**Important:** Gauntlet demonstrates local capability boundaries. It does not demonstrate verified ArmorIQ policy enforcement or production-grade security.

## Problem and motivation

Prompt injection can steer an AI agent toward actions outside the user's intended task. One important defense is least privilege: an agent should only have access to the tools it needs.

Gauntlet illustrates this principle by comparing simulated attack scenarios and testing how different local permission profiles restrict tool availability.

## How Gauntlet works

The Python backend uses a local tool registry and dispatcher. When a permission profile is selected, the dispatcher checks whether the requested tool belongs to that profile's allowlist before proceeding to policy evaluation and tool invocation.

The browser dashboard communicates with a small Python HTTP server bound to `127.0.0.1`. The dashboard uses local simulation results and does not make ArmorIQ or other external service requests.

The publishing tool is a harmless local no-op stub. It returns a simulated result and does not publish content, transmit data, or call an external service.

## Simulated attack scenarios

- **Unguarded agent:** The simulated agent follows a dummy injected instruction. Its local registry includes `publish_report`, which reaches the no-op publishing stub.
- **Least-privilege agent:** Its registry contains only `research`. A publishing attempt is unavailable because `publish_report` is not registered, so no publishing function is invoked.

These scenarios illustrate the difference between tool availability and restricted capabilities. Their outcomes are generated by local simulation logic, not real ArmorIQ policy decisions.

## Permission profiles

The dashboard provides three profiles with distinct local tool grants:

| Profile | Available tools | Purpose |
| --- | --- | --- |
| Read-only | `research` | Restricts the agent to the research tool. |
| Limited Access | `research`, `gauntlet__echo` | Adds access to a harmless local echo tool. |
| Admin Simulation | `research`, `gauntlet__echo`, `publish_report` | Demonstrates expanded access, including the local no-op publishing stub. |

The dispatcher enforces the selected profile's tool allowlist before invoking a registered tool. Unknown profiles are rejected.

**Admin Simulation is not a real administrator role.** The profile and publishing operation are part of the local demonstration; they do not grant external privileges or publish anything.

## Architecture and project structure

- `gauntlet_demo.py` - local tool dispatcher, permission profiles, simulated attack scenarios, and command-line demonstrations.
- `gauntlet_echo.py` - independent local echo function.
- `policy_decision.py` - helper for interpreting and formatting a supplied decision object; it does not contact ArmorIQ.
- `gauntlet_web.py` - standard-library localhost server and dashboard JSON adapter.
- `web/index.html` - dashboard markup.
- `web/styles.css` - dashboard styling.
- `web/app.js` - dashboard behavior and display logic.
- `run_policy_live.py` - separate ArmorIQ SDK example that may contact the configured service when run.
- `requirements.txt` - pins `armoriq-sdk==0.6.10` for the separate SDK example.
- `armoriq.yaml` and `.env` - local configuration files that must remain private and must not be committed.
- `test_*_offline.py` - offline tests for dispatch, permission profiles, simulated decisions, and dashboard behavior.

## Requirements and installation

Gauntlet's local dashboard, demonstrations, and offline tests use Python 3 and the standard library. No third-party package installation is required for these workflows.

From a clean Windows checkout, create a virtual environment:

```powershell
py -3 -m venv .venv
```

The separate ArmorIQ SDK example requires its pinned dependency. Install it only when preparing that example:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

The SDK example also requires a valid, authorized ArmorIQ configuration. Keep local configuration and credentials out of public commits.

## Launching the dashboard

From the project root, run:

```powershell
.\.venv\Scripts\python.exe gauntlet_web.py
```

Open [http://127.0.0.1:8000](http://127.0.0.1:8000) in your browser and select **Run Attack Simulation**.

Stop the server with `Ctrl+C`.

To use a different port:

```powershell
.\.venv\Scripts\python.exe gauntlet_web.py --port 8010
```

## Running the command-line demonstrations

Run the prompt-injection scenarios:

```powershell
.\.venv\Scripts\python.exe gauntlet_demo.py --prompt-injection
```

Run the local echo demonstration with a simulated allow decision:

```powershell
.\.venv\Scripts\python.exe gauntlet_demo.py "hello" --decision allow
```

Run it with a simulated deny decision:

```powershell
.\.venv\Scripts\python.exe gauntlet_demo.py "hello" --decision deny
```

These commands demonstrate local behavior. They do not invoke ArmorIQ.

## Running the offline tests

From the project root, run:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
```

The latest recorded local test run passed all 26 tests. The suite covers tool dispatch, simulated authorization decisions, permission-profile grants, rejected profiles, and dashboard behavior.

The offline tests use the standard library and do not initialize a live ArmorIQ client or require external network requests.

## ArmorIQ integration status and limitations

`run_policy_live.py` is separate from the local dashboard and offline tests. It loads ArmorIQ configuration and performs an SDK session/check flow. Running it may contact the configured service.

Endpoint connectivity and the saved credential's authorization for the intended environment remain unverified. A successful live policy decision has not been demonstrated.

The current SDK path does not pass through or enforce `require_csrg: true`. The local tools are not registered with ArmorIQ, and dashboard outcomes are generated by Gauntlet's local simulation logic.

Do not interpret simulated outcomes, permission profiles, or offline test results as verified ArmorIQ policy enforcement. Gauntlet is a prototype, not a production security system.
